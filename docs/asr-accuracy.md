# 识别准确率排查手册 · Chan 会议记录

> 目标：把"识别不准"拆成可测量的几层，逐层排除，而不是凭感觉调参数。
> 现状：链路本身已验证能准确识别（见 §2），剩下的是"设备实际录到的声音"。

## 1. 链路参数核对（逐项有据，不是估计）

| 环节 | 实际配置 | 结论 |
| --- | --- | --- |
| I2S 采集 | `cfg.sample_rate=16000`、`stereo=false`、`magnification=16`、`noise_filter_level=0` | I2S 时钟直接 16k，**无软件重采样** |
| 帧封装 | `FRAME_SAMPLES=800` = 50ms = 1600 字节，int16 **小端**、mono | 字节序与百炼要求一致 |
| 传输 | WS 二进制帧，裸 PCM，不 base64、不加时间戳 | TCP 有序，不需要序号 |
| 网关 | 透传，不改采样、不切片 | — |
| 调用参数 | `paraformer-realtime-v2`、`format=pcm`、`sample_rate=16000`、`language_hints=["zh"]`、`vocabulary_id`(热词) | 与采集严格一致 |
| 回显 | `p/f` JSON → 屏幕 120ms 重绘节流 | — |

**结论**：44.1k/48k 立体声直传、8k 默认值、软重采样这些"头号元凶"在本项目里**都不存在**（代码里 `record(micBuf, 800, 16000)` 显式指定，与 I2S 配置同值）。
剩下的真实变量只有两个：**录进来的声音质量**、**设备端 VAD 裁掉了什么**。

## 3. 今天修掉的三个真问题（都会"看起来像识别不准"）

### 3.1 WebSocket 重连风暴（最严重）

`WebSocketsClient::loop()` 的判断是 `if (millis() - _lastConnectionFail < _reconnectInterval) return;`
——`setReconnectInterval(0)` 意思是**失败后 0ms 重连（无限速）**，不是"关闭自动重连"。
之前所有想关重连的地方都写的 0，结果空闲页一旦冒出连接就变成风暴：**实测 2 分钟 319 次接入**，
每次都让网关新开一个百炼 task（撞 QPS、抢上行连接、真会话被挤到专用连接）。
表现就是"有时候能识别、有时候卡住"。

修：`WS_RECONNECT_OFF_MS = 1 天` 来表达"关闭"，需要会话时 `connectSession()` 改回 3s。

### 3.2 WiFi 的两个坑

- **modem sleep**：默认 `PS_MIN_MODEM` 会把上行帧憋到 DTIM 信标才发，平白多 100~300ms 抖动 → 回显慢半拍。改 `WIFI_PS_NONE`。
- **路由器偶发拒绝关联**：日志实测 `reason=2 (AUTH_EXPIRE)`、`reason=208 Association refused temporarily`
  （ESP32 已知问题，comeback time 解析成 0xFFFFFFEA 这种越界值）。原来只 `WiFi.begin()` 一次，失败就躺平；
  现在每 10s 自动重试并打印 reason code，实测 3 秒内自愈。

### 3.3 采集 DMA 缓冲 256ms → 768ms

整屏重绘 + 网络抖动会占几十 ms，缓冲太浅（256×16）就溢出丢采样 → 丢字断词。
改 `dma_buf_len=512 / count=24`（≈0.77s）。

另外 `WS_RECONNECT` 修好之后，建会话从 **1.5s 降到 0.10s**（百炼上行连接预热复用）。

## 4. 现在怎么定位"到底哪儿不准"（3 步，30 分钟）

**第 1 步：录一段 30 秒**
正常音量、嘴离设备 10~30cm，念一段包含专有名词的话（人名、产品名、业务词）。

**第 2 步：看串口的 `[AUD]` 三行**（新加的音频体检）

| 指标 | 正常范围 | 异常含义 |
| --- | --- | --- |
| `peak` | ≈ -6dB（-3 ~ -12 可接受） | 接近 0dB → 快削波，破音必错字 |
| `rms` | -25 ~ -35dB | < -50dB → 声音太小，远场信噪比不够 |
| `clip` | < 0.1% | > 1% → 已削波（增益过大/离太近/结构共振） |

**第 3 步：`make rec` 下载 WAV，用 Audacity 听**
（网关侧也有一份"音频体检"日志，`journalctl -u meeting-gw | grep 音频体检`）

| 听感 | 判定 | 下一步 |
| --- | --- | --- |
| 清晰、无破音 | 采集链路 OK | 加热词 / 调 VAD / 换模型 |
| 破音、爆音 | 削波 | 降 `magnification`（16→8）或拉开距离 |
| 闷、远、底噪大 | 信噪比不足 | 靠近、加防风棉、远离风扇/空调 |
| 句子之间几乎没停顿 | VAD 裁掉了静音 | 见 §5 定稿延迟 |

> 网关存的是 **VAD 之后**的流 —— 正好能听出句首有没有被裁掉。这是它比"设备本地录"更有用的地方。

## 5. 如果 WAV 清晰，但仍有个别错字

按性价比排序：

1. **补热词**（最高性价比，已做）：`assets/terms.txt` 一行一个词 → `make deploy` 自动重建热词表，
   `vocabulary_id` 随 run-task 下发。实测 26 词已生效。
2. **试关 VAD**：`VAD_ENABLE=0` 对比同一段话。会议是远场说话，9dB 门槛可能吞掉轻声字的句尾/句首
   （预滚只补 400ms，补不回被整段抑制的弱音）。
3. **定稿慢导致的"回显跟不上"**：VAD 把静音删掉后，服务端等不到 800ms 静音就迟迟不判句尾，
   屏幕一直刷 partial、越刷越长。若 WAV 里句子间几乎没有空档，把 `VAD_HOLD_MS` 提到 1200ms
   或给 parameters 加 `max_sentence_silence`（需实测确认该参数对该模型有效）。
4. **语种**：`language_hints=["zh"]`；中英混说多的会议可试 `["zh","en"]`。
5. **会后重识别**：实时流只求快；要准就存 WAV → `paraformer-v2` 文件识别（可开 `diarization_enabled` 分人），
   再喂 LLM 出纪要。WAV 落盘已经具备，这是下一步 P1。

## 6. 不建议做的（附理由，免得反复纠结）

| 方案 | 为什么不建议 |
| --- | --- |
| 400ms 大包 + 时间戳 + 服务端拼接 | WS 在 TCP 上天然有序，PCM 是连续流，百炼不需要时间戳；包越大首字延迟越高。50ms 帧已是最优折中 |
| 设备端软件重采样 | 已经硬件直采 16k，再重采样只会引入失真与算力开销 |
| CoreS3 跑 WebRTC NS | S3 内存/算力紧张，收益不如物理降噪（防风棉、远离风口） |
| base64 信封 + seq + session_id | 体积 +33%，纯损失；WS/TCP 已保证顺序 |
| 直接发 44.1k 立体声让服务端降采样 | 百炼按声明参数解析，格式不符直接乱码 |

## 8. 复盘：真正的原因不是音频，是模型（2026-10-23 夜）

上一版把"识别不准"归到音频链路（增益低、底噪高、VAD 吞音），方向错了。用真实录音做
**同音频、换模型** 的对照实验后，结论非常干脆：

### 8.1 同一段 18 秒真实录音，三个引擎的定稿

原始音频：50.9s 设备实录，切 14~32s，rms −29.9dBFS（比 TTS 基准低 15dB）。

| 引擎 | 定稿文本 |
| --- | --- |
| `paraformer-realtime-v2`（原用） | 内匿名报料号二手网站消有方时，部分人是内属于猜测无法。 / 在货费相关的。 / 不能被当成事实定论。 |
| `qwen3-asr-flash`（整段，仅作参照） | 这些全部是圈内匿名爆料号的二手网传消息，没有官方实锤，部分是圈内估值猜测，无法百分之一百锁定，存在错配、张冠李戴的风险，这些过往传版的对标，不能当成事实定论。 |
| `qwen-audio-3.0-asr-flash-streaming`（现用） | 这些全部是圈内匿名爆料号的二手网传消息，没有官方实锤，部分圈内估值猜测，无法100%锁定，存在错配、张冠李戴的风险，只做网传版本对标，不能当成事实定论。 |

音频一个字没改，只换模型，结果从"不可用"到"基本可直接用"。所以 **§1 的参数核对虽然全对，
但它只能证明"格式没错"，不能证明"模型能扛住真实环境"**。

### 8.2 为什么被 TTS 样本骗了

`paraformer-realtime-v2` 在我合成的 TTS 音频上逐字全对（含模块/接口/数据同步/异常处理），
所以当时判了"链路 OK"。TTS 是**无噪声、无房间混响、电平拉满**的理想音频；真实麦克风是
**−40dBFS 底噪 + 15dB SNR + 15dB 偏低电平**。paraformer 对这种降级极度脆弱，而 Qwen 系列
是 LLM-based，抗噪能力完全不是一个量级。

**教训：验收样本必须来自真机真环境，合成音频只能验通路，不能验准确率。**

### 8.3 顺带发现的连带症状：定稿比中间结果还短

paraformer 在句子结束时会丢字：

```
sid=2 中间结果: 在货费相关理财的风险
sid=2 定稿:     在货费相关的
```

已用 `scripts/ds_probe.py`（直连百炼打印每条原始事件）验证：**丢字发生在百炼服务端**，
不是网关转发的问题；关标点预测（`punctuation_prediction_enabled=false`）、调
`max_sentence_silence`、开 `semantic_punctuation_enabled` 都救不回来。它是模型"不确定"
时的连带症状，换模型后自动消失（定稿 2590-16350ms 一次给出完整一句）。

### 8.4 改动

| 位置 | 改动 |
| --- | --- |
| `gateway/app.py` | `ASR_MODEL` 默认改 `qwen-audio-3.0-asr-flash-streaming`；`/opt/meeting-gw/.env` 同步 |
| `gateway/app.py` | 热词改用**内联模式** `parameters.vocabulary = {"词": 5}`（该模型支持，免建表）；paraformer 的 speech-biasing 建表逻辑保留兼容 |
| `gateway/app.py` | 热词缓存增加 `model` 字段校验：不同模型的热词表互不通用，拿旧 id 去 update 会静默失效 |
| `firmware/config.h` | `VAD_ENABLE 1 → 0`：静音帧必须照发。云端靠句间静音断句，丢静音等于让模型永远等不到句尾 |
| `scripts/ds_probe.py` | 新增：直连百炼逐事件打印，排障必备 |

### 8.5 已被实验否掉的猜测（别再走回头路）

| 猜测 | 实测结果 |
| --- | --- |
| 直流偏置 | 均值 = 1，载荷 0.0%，干净 |
| 开机爆音致削波 | 0.138s 有一个 −32752 的弹麦尖峰，但它只是一次性瞬态，不在语音段 |
| 采样率/位深/声道错配 | 16k/16bit/mono，时长与墙钟 1:1，无变速变调 |
| 功频干扰 | 50/100/150Hz 无突出峰（突出 −3.5~+4.5dB，属正常起伏） |
| 电平太低 | rms −33dBFS 确实偏低 15dB，但把音频归一化后 paraformer 依旧一样错 → 不是主因 |

电平偏低与弹麦尖峰仍值得修（属 P2 音质优化），但它们**不是这次识别不准的原因**。

## 9. 复盘：屏幕上的灰字为什么没变成正文（2026-10-23 深夜 · v0.5.1）

**现象**：说话过程中屏幕上出现浅灰色文字（partial），之后既没变成白色正文，手机端记录里也查不到这一句。

**根因不是识别，是"定稿事件"在两个地方被丢掉。**

### 9.1 网关：空定稿被直接跳过

百炼的 `result-generated` 事件里，`sentence_end=True` 时 `text` 可能是空串。这不是异常，是**模型对这一段置信度不足时的正常行为**——它检测到有语音活动，但不敢输出文字。

实测一段英文电影对白（45 秒，rms −36dBFS 的远场录音），16 个句子里有 **13 个是空定稿**：

```
sid=2  end=True  4580-6080ms  ''
sid=3  end=True  9210-11280ms ''
... 共 13 句
```

旧代码遇到空文本直接 `continue`，**什么事件都不发给设备**。于是：

- 设备侧那句灰字收不到 `f`（定稿），永远停在灰色
- 会议记录里也不会有这一句

### 9.2 固件：收尾时把 partial 直接清空

用户说到一半按停止，最后半句必然还在 partial 状态（百炼要等 800ms 静音才判句尾）。这时：

| 位置 | 旧行为 | 后果 |
| --- | --- | --- |
| `done` 分支 | `gPartial = ""` | 最后半句内容蒸发 |
| `ST_STOPPING` 超时 | `gPartial = ""` | 同上 |
| `ST_PAUSING` 超时 | `gPartial = ""` | 同上 |

三处都是"清空"而不是"提交"，等于把用户最后说的那半句直接扔掉。

### 9.3 修法：所有 partial 都必须有归宿

**网关**按 `sid` 缓存"这一句最后一版有字的文本"，兜三个口子：

| 场景 | 处理 | 日志标记 |
| --- | --- | --- |
| `end=True` 但文本为空 | 用缓存的 partial 补成定稿 | `(空定稿补字)` |
| `task-finished` 时还有句子挂在 partial | 全部补成定稿 | `(收尾补定稿)` |
| 设备断线 / 异常退出 | 未定稿内容直接写进会议记录 | `断线补记` |

**固件**抽出 `commitText()`，`done`、`STOP_TIMEOUT` 三处统一改为"先提交再清空"。

### 9.4 顺带修掉的语言问题

`language_hints` 原来只写 `["zh"]`。模型遇到英文段时，会把整段判成噪音、返回空文本。改成 `["zh", "en"]`：

| 音频 | 只标 zh | zh + en |
| --- | --- | --- |
| 中文测试句（35.6s） | 6 句定稿 | 6 句，内容一致（反而多识别出一个"嗯"） |
| 英文电影对白（45s） | 16 句里 13 句空 | 空句减少，能多捞回整句 |

会议里夹杂 KPI / ROI / AWS 这类英文是常态，加 `en` 没有代价。

### 9.5 验证方式：造病态事件流

真实音频很难稳定复现"有 partial 无定稿"，所以起了一个假百炼服务，精确造出两种病态事件：

```
场景 1：sid=1 连发两版 partial → 然后 end=True 且 text=''
场景 2：sid=2 只发 partial → 随后 finish-task，永远没有 end
```

断言结果：

```
定稿(空定稿补字) #1 这是第一句的完整内容
定稿(收尾补定稿) #2 第二句话说到一半就停了
```

会议 JSON 里两句都在。改动前这两句全部消失。

### 9.6 以后怎么自查

```bash
# 有没有出现兜底（出现说明那一段模型信心不足，但内容救回来了）
ssh aliyun 'journalctl -u meeting-gw | grep -E "空定稿补字|收尾补定稿|断线补记"'
```

如果这类日志很多，说明现场音频质量或模型信心有问题，该往 §4 的电平体检和 §5 的音质优化走。但**内容不会再丢**。

## 10. 实测：换成 qwen3-asr-flash-realtime 能不能解决问题？（2026-10-23 深夜）

起因：v0.5.1 用户评分 80%，剩余痛点是"慢 / 偶尔不准 / 偶尔漏"，
提议改用百炼 `qwen3-asr-flash-realtime`（OpenAI Realtime 兼容协议）。

### 10.1 先纠正两处协议错位

| 提议里的说法 | 实际情况 |
|---|---|
| `from dashscope.audio.asr import Recognition, RecognitionCallback` | 这是 **paraformer-realtime** 的 SDK 类，**不适用于** qwen3-asr-flash-realtime。后者只有 WebSocket 事件协议，没有这个 Python SDK 封装 |
| "在 ECS 上起一个中转服务" | **已经是这个架构**。设备 → meeting-gw（阿里云）→ 百炼，网关就是中转。要换的只是网关到百炼这一段 |
| `pcm, 16000, mono, 16bit 小端`、3200 字节一包 | **完全正确**，且现有固件已经是 3200 字节分包 |
| partial / sentence_end 区分 | 现有协议已有：`{"t":"p"}` 增量 / `{"t":"f"}` 定稿 |

真实协议（已跑通，见 `scripts/realtime_probe.py`）：

```
wss://dashscope.aliyuncs.com/api-ws/v1/realtime?model=qwen3-asr-flash-realtime
Authorization: Bearer <key>

→ {"type":"session.update","session":{"input_audio_format":"pcm","sample_rate":16000,
                                      "input_audio_transcription":{"model":"...","language":"zh"}}}
→ {"type":"input_audio_buffer.append","audio":"<base64 3200B>"}   # 循环
→ {"type":"session.finish"}

← session.created / session.updated
← input_audio_buffer.speech_started / speech_stopped / committed   # 服务端自带 VAD
← conversation.item.input_audio_transcription.text       # 增量，文本在 stash 字段！text 常为空串
← conversation.item.input_audio_transcription.completed  # 定稿 transcript
← session.finished
```

**两个坑**：
1. `input_audio_format` 必须是 `"pcm"`，写 `"pcm16"` 直接 1011 报错断连。
2. 增量文本落在 **`stash`** 字段里，`text` 是空字符串 —— 只读 `text` 会以为它不回显。

### 10.2 同段真机录音 A/B（/tmp/t50.wav，50.9s）

音频能量：17–30.7s 是真人说话（−24~−33dBFS），前后都是 −39dBFS 底噪，SNR 约 14dB。

| | qwen-audio-3.0-asr-flash-streaming（线上） | qwen3-asr-flash-realtime |
|---|---|---|
| 识别文本 | 这些全部是圈内匿名爆料号的二手网传消息，没有官方实锤，部分圈内**故事**猜测无法100%锁定，存在错配张冠李戴的风险，**只做**网传版本对标，不能当成事实定论 | **本部**是圈内匿名爆料号的二手**网站**的消息，没有官方实锤，部分是圈内**共识**猜测，无法百分之百锁定。存在错配、张冠李戴的风险，**是过往船板**的对标，不能当成事实定论 |
| 错处 | 2 处（故事猜测 / 只做） | 3 处（本部 / 二手网站 / 船板） |
| 事件数 | 153（134 增量 + 19 定稿） | 87（85 增量 + 2 定稿） |
| 空文本事件 | **128 / 153 = 84%** | 0 |
| 断句 | 19 句（底噪段疯狂切出 18 个空句） | 2 句，VAD 断在 16.9/24.0/30.7s，与能量图完全吻合 |
| 首字延迟 | 与语音同步（语音段一起就有增量） | 语音起点 +1.5s |

### 10.3 结论：换模型不是杠杆

1. **准确度没有提升**，反而多错一处。两者错误都集中在专名和近音词，是 SNR 14dB 的物理限制，不是模型选型问题。
2. **"84% 空事件"不是设备变慢的原因** —— 网关 `downlink()` 里 `elif txt:` 早就把空增量拦了，空定稿也只 `committed.add()` 不下发。这些事件只消耗网关侧的 JSON 解析。
3. realtime 确实更干净（自带 VAD、零空事件、断句准），但代价是准确度掉，且要另写一套协议适配层。**收益不抵成本。**
4. 官方评测口径也印证：Qwen3-ASR Flash 的 WER 6.04% 优于 Fun-ASR 7.60%，但注明"轻声和实时首字较弱"—— 我们这种底噪 15dB 的现场正是它的弱项。

### 10.4 真正的三个杠杆（按性价比排序）

**① 会后精转（最高性价比，直接解决"不准"）**

实时这条链路的天花板是"必须边听边出字"，用不上后文上下文。而百炼有
`Qwen-Audio-3.0-ASR-Flash-Filetrans`（异步文件转写）和 `fun-asr-flash`（HTTP，
≤5 分钟，支持**前文对话上下文** + 热词 + 语音润色）。录音已经落盘在
`recordings/`，完全可以在会议结束时用整段录音重跑一遍，替换 `meeting.py` 里的
原文再生成纪要。**流式负责看得见，离线负责存得准**，这是行业标准做法。

**② 提升 SNR（解决"不准"的根本）**

现在远说 −33dBFS / 近说 −19.5dBFS，动态范围差 14dB；底噪 −39dBFS。
硬件增益只有 4 倍（+12dB），已到芯片上限。能动的只有麦克风距离和固件侧
软件增益/降噪。**换任何模型都不如把 SNR 提 6dB 有效。**

**③ 回显延迟定位（解决"慢"）**

需要先量清楚：设备采集 → 网关转发 → 百炼首个增量 → 回显上屏，
四段各占多少毫秒。现在只有"感觉慢"，没有分段数据，动代码都是猜。

### 10.5 判定

- 换 `qwen3-asr-flash-realtime`：**不做**。
- 会后 Filetrans 精转：**值得做**，是唯一能真正提升"准确度"的路径。
- 探针脚本已留 `scripts/realtime_probe.py`，以后要验证任何流式模型直接 `--raw` 跑。

## 11. 评估两个参考项目：有没有值得抄的（2026-10-23 深夜）

### 11.1 `limengdu/XIAO-ESP32S3Sense-Speech2ChatGPT` — ❌ 无借鉴价值

链路比我们落后一代：

| 维度 | 它 | 我们 |
|---|---|---|
| 录音 | **固定 10 秒**，无 VAD，录完才发 | 连续流式，边说边发 |
| 上传 | 整个 WAV **一次 HTTP POST** | WS 二进制帧，3200B/100ms |
| 增益 | `sample <<= 2` **硬左移** | `f_gain` 归一化，带 offset 自动归零 |
| 屏幕 | LVGL + TFT_eSPI + SquareLine | M5GFX 直接画，无额外依赖 |

`<<2` 那个增益是反面教材：无削波保护，遇到大声直接顶到 int16 上限，波形削平成方波，ASR 反而更差。它的 README 自己也没提 VAD 和流式 —— 那是固定时长录音的必然结果。

**唯一可看的是它把 I2S 采集放进独立 RTOS 任务**。但我们单核 loop 里 `M5.Mic.record()` 已经能跟上（768ms 缓冲），上 FreeRTOS 只会增加同步复杂度。

### 11.2 `espressif/esp-adf` → `adf_examples/ai_agent/esp_llm_tongyi_agent_app` — ⚠️ 只有一半可用

（注：原帖路径 `examples/ai_agent/esp_llm_tongyi_agent` 已失效，现挂在 `adf_examples` 组件里，底层是 `esp_llm_service`。）

**不值得抄的**：

- `esp_llm_service` 的四流架构（AUDIO_UP / VIDEO_UP / AUDIO_DN / VIDEO_DN）+ 事件总线 —— 我们没有视频、没有播放，为一个单向录音流套这层壳属于自找麻烦。
- 上行 **OPUS 16kHz** 编码 —— 我们走 WiFi 局域网，32KB/s 裸 PCM 完全不构成瓶颈，加编解码只增延迟。

**看起来能抄、实际是坑的两个**（已核对 M5Unified 源码）：

1. **`noise_filter_level`** —— 名字像降噪，实现是
   ```c
   v = (raw * (256 - level) + prev * level + 128) >> 8;   // 单极低通 IIR
   ```
   `level=2` 截止约 7kHz，`level=4` 砍到 3.5kHz —— 正好切掉 /s/ /ʃ/ /f/ 这些清辅音的能量。**开着就是自毁识别率**，所以固件里写 0 是对的。

2. **提高 `magnification`** —— 真实算式在 `Mic_Class.inl:620`：
   ```c
   f_gain = magnification / (over_sampling << 1);   // 16 / 4 = 4.0
   ```
   纯**数字**增益，ADC 之后才乘。底噪和信号一起放大，SNR 一个 dB 都不涨，只会更早削波。

**唯一有价值的是 AFE 的 AGC 参数口径**（供以后真要写时参考）：

```
target_dbfs   -20 ~ -16
max_gain_db   30
attack_ms     100
release_ms    500
```

但它救不了我们 —— 因为我们缺的不是"音量不够"，是**信噪比不够**（语音 −24~−33dBFS / 底噪 −39dBFS）。AGC 把整体拉大，底噪同样变大。

### 11.3 一个被评测否掉的方向

第三方横评（7 款 ASR，真实会议录音）明确结论：**降噪能改善听感，但对识别率基本没有帮助**。
所以"在网关侧加 RNNoise / DeepFilterNet 再送百炼"这条路，投入产出比很低，不排期。

### 11.4 净结论

| 方向 | 判定 |
|---|---|
| 抄项目 1 的采集/上传 | ❌ 落后于现状 |
| 迁到 ESP-IDF + esp_llm_service | ❌ 架构过重，收益为零 |
| 设备端 AFE（NS/AGC/VAD） | ❌ Arduino 下接 esp-sr 预编译库对 IDF 版本敏感，且 AGC 救不了 SNR、设备端 VAD 还会破坏云端句尾判断（v0.4.x 已踩过） |
| 网关侧降噪 | ❌ 评测不支持 |
| **会后 Filetrans 精转** | ✅ 唯一还能动的 |

一句话：这两个项目解决的是"怎么把音频送出去"，而我们的瓶颈早就不在送出去，在**送出去的东西本身信噪比只有 14dB**。

## 12. 会后精转 + 说话人分离（v0.6.0 · 2026-10-23 深夜）

§10 和 §11 的结论都指向同一件事：**流式链路的天花板是"必须边听边出字"**，用不上后文语境。
录音既然已经完整落盘，散会后拿同一段音频用离线大模型重跑一遍，才是提升准确率唯一还有空间的地方。
顺带把说话人分离也做了 —— 会议记录没人名，价值本来就打了对折。

### 12.1 选型：为什么不是 paraformer

| 模型 | 说话人分离 | 判定 |
|---|---|---|
| `paraformer-v2` | `diarization_enabled` + `speaker_count`(2~100) | ❌ **不用**。§8 已实测：真实麦克风音频上它输出"内匿名报料号二手网站消有方时"，抗噪不过关，加不加 diarization 都没意义 |
| `fun-asr` | 支持 | ⚠️ 可用，但评测 WER 7.6%，且 `language_hints` 只吃 1 个语种 |
| **`qwen-audio-3.1-asr-flash-filetrans`** | 支持 | ✅ **选中**。2026-09-23 发布，官方明确"复杂噪声环境下仍能保持稳定"，正好对着我们 14dB SNR 的现场 |

三者共用同一套异步 API（提交 → 轮询），所以换模型只是改一个字符串。

### 12.2 实测数据（339 秒真实录音 `6adb6f29`）

| | 流式（qwen-audio-3.0-streaming） | 精转（3.1-filetrans） |
|---|---|---|
| 句数 | 28 | **54** |
| 说话人 | — | **3 人**（4 / 44 / 6 句） |
| 耗时 | 实时 | **6.5 秒**（约 52 倍速） |
| 典型质量 | "感入关明的是" / "不是我" / "T." / "对" | "哦，出口好像打开了" / "时间到了时间到了" / "这东西我后面还有一一串呢" |

流式那堆碎片正是底噪段被硬切出来的结果；精转拿到完整上下文后，句子边界和内容都正常了。

**纪要质量同步提升**：带着「发言人N：」前缀喂给 qwen-plus 后，纪要能写出"发言人2、3反复互动"这种归属关系。
抽查了纪要里的细节（立定跳远、三花猫、《九星》，以及 1.6 米 / 2.3 米成绩）—— 全部能在精转原文里找到对应句子，**不是模型编的**。

### 12.3 三个必须记住的坑

1. **`parameters` 字段必须传**，哪怕是个空对象 `{}`。新版业务空间域名下省略这个字段，任务能提交成功但查询时返回识别失败 —— 静默失败，最难查。
2. **`file_urls` 必须是外网可达的绝对 URL**，百炼自己来拉。所以公网录音地址（`/m/<key>/<id>/audio`）正好复用了。
3. **必须等 WAV 头补写完再提交**。录音是边收边写、结束后才补 RIFF 头的，提前提交会拉到残包。所以精转的触发点从 `done` 事件挪到了 `finally` 里 `_rec_close()` 之后。

### 12.4 实现

`gateway/meeting.py` 新增：

```
audio_url(rec)      拼公网录音地址
refine(rec)         提交 → 轮询(2s×150) → 下载结果 → 替换 sentences
dialogue_text(rec)  带「发言人N：」前缀的对话文本，喂给纪要模型
finalize(rec)       会议收尾唯一入口：先精转，再生成纪要
```

- `sentences` 结构从 `{s,t,b,e}` 扩成 `{t,b,e,spk}`，`spk` 是 1 起的发言人编号，按**首次出现顺序**重排（原始 `speaker_id` 是 0 起的算法编号，直接显示会让人困惑）
- 原始流式结果**不丢**，整个存进 `sentences_stream` 留作对照
- 精转失败不影响纪要：退回流式文本照常生成，页面标注"精转未成功"
- `app.py`：`persist_meeting()` 不再直接拉纪要，统一由 `finally` 里的 `mt.finalize()` 拉起，保证"录音关闭 → 精转 → 纪要"的顺序

前端：文字记录按发言人着色（`.s1`~`.s5` 五色循环），顶部显示"N 位发言人"，
列表页给精转中的会议挂「精转中」徽标。

### 12.5 关掉的方式

```bash
FILETRANS_ENABLE=0     # 完全关掉会后精转，退回纯流式
FILETRANS_MODEL=...    # 换模型（同协议即可，如 fun-asr）
SPEAKER_COUNT=4        # 给人数一个参考值；2~100 才合法，填 1 会报错
```
